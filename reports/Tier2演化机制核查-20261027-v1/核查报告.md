## 1. 最重要的结论（500字以内）

B1初始化看到10个H的说明与完整代码、七状态和SELECT/MIX规则，后续初始化还看已接受U的代码档案，不看成绩。B2和EVO用5个手工静态U作P0，不调用LLM初始化；IND每次只看H0/H1及接口，不看P0或搜索历史。常规CROSS/MUTATE收到父代源码、说明和H语义，不收到父代总分、逐实例成绩或行为反馈；仅CROSS成绩反馈B组增加两父代总Fitness及差值。Fitness在外部用于父代排名抽样及代末父子合并取前N；没有行为多样性奖励。B1的5→3→2是真实21实例完整物理排程分组，不是源码数或仅Cmax分组。P2中4个不同源码U实际输出序列相同；另1个冠军改善。因此已有有限训练行为趋同证据，但不能据此证明早熟收敛，或证明趋同导致搜索失败。

### 2.3 发送路径：保存了什么，不等于发了什么

- B1 `_prepare()`构造Prompt并落盘；`Search._attempt()`只把`pending['prompt']`交给请求账本；最终传输器发送该字符串。
- IND/EVO `execute_task()`保存任务父代ID、源码key和Prompt，然后调用`journal.request()`；完整成绩在响应后评价、提交和更新群体时才使用。
- CROSS A/B在准备期固定30个Prompt；实际执行器读取这些文件请求，不在运行时额外加入逐实例表或反思文本。
- API发送单次Prompt，不自动把checkpoint、结果文件或整个工作区交给模型。元数据存在磁盘上不是上下文输入。

### 3.2 父代是排名加权、不放回抽样，不是按Fitness数值比例抽样

`select_parents()`先按`(-Fitness, id)`排序。原种群大小N、从0开始的排名r，抽样权重为：

```text
w_r = 1 / (N + r)
```

每选一个就移出候选池，同时移出其原权重；不重新计算剩余者的名次权重。Fitness影响排名，但两者分数差距不直接进入概率。

**N=5、CROSS也取5时，五个成员全部都会进入该请求；排名偏好主要改变展示顺序。** B1 CROSS只取2，因此会影响父代成员集合；MUTATE取1，亦影响哪个父代被修改。不能简单说所有交叉都“更常选到最好父代而不选其他父代”。

源码：[原搜索select_parents](../../code/fjsp_usage/research/evolution.py)、[当前通用抽取版本](../../code/heuristic_design/core/search.py)。本次实际请求父代ID与这套机制及已存随机数状态一致；新B1补跑已有[专门核验](../b1-p1-to-p2-T15-seed501-20261027-v1/Closeout_summary.json)。

### 3.3 真实流程伪代码

```text
B1: P0 = 首先获得的5个完整有效、AST不重复的LLM初始化U
B2/EVO: P0 = 预先冻结的5个手工静态权重U

for generation in 两代:
    父代池 = P_g                         # 代内冻结
    C_g = []
    for slot in 0..9:
        op = CROSS if slot < 5 else MUTATE
        parents = 按固定代种群排名，不放回抽取(op规定的个数)
        response = 请求一次候选；仅已证实的临时传输失败可按协议重试
        if 无完整响应 / 非法代码 / AST重复:
            消耗槽位，不免费补员
        else:
            result = 完整实例首解＋复检及身份/生命周期认证
            if 有效: C_g.append(子代)
            if 普通已认证超时: 子代无效，Fitness=null
            if 身份/终态/账本未知: Stop，保留证据
    P_(g+1) = sorted(P_g + C_g, key=(-Fitness, id))[:N]
```

子代在本代只进入children，**不能立即成为本代后续请求的父代**。每代只更新一次。`ranked(parent+children)[:N]`是精英式保留：最好Fitness不会因随机保留而下降，但并不保证特定旧代码在同分时一定留下；同分按id决定，不按行为新颖性。

关键位置：[Search._attempt/run](../../code/fjsp_usage/research/evolution.py)、[B1固定父代池](../../tools/b1_usage_local.py)::`_prepare()`、[IND/EVO advance](../../tools/ind_evo_h01.py)、[当前通用survive](../../code/heuristic_design/core/search.py)。

### 3.4 去重、多样性与异常处理

- B1/B2使用历史seen里的验证AST key去重；不是源码字符相似度、平均Fitness相等、排程相同或状态行为距离去重。AST规范化不等于广泛语义等价。
- IND/EVO按各自unit的seen判断重复；严格匹配的评价可缓存展示，但重复不作为新颖子代加入群体。不同unit可共享物理缓存，逻辑槽仍计入预算。
- 当前通用CLI也会记录AST_duplicate并复用评价；演化children只接纳`not AST_duplicate`的有效子代。生存函数本身仍只是排名截取。
- 无行为新颖性奖金、随机保留名额、按物理排程分组限额，或基于共同状态的父代多样性抽样。
- `sets.py`确实有`complementary_parents/survival`：按逐实例成绩向量的互补性选H阶段父代／幸存者，不是按U物理行为选种群。`Search.run()`只有`arm=='H'`才走该生存分支；本次B1、B2都为内部arm B，不能将此函数算作已经启用的U多样性机制。
- 静态诊断字段只用于外部审计；没有进入Fitness、排名或生成反馈。旧基类对某些中断缓存会保守标无效，新IND/EVO与接续入口对未知状态采用Stop；不能笼统地说所有异常都会继续。

证据：[去重和评价](../../code/fjsp_usage/research/evolution.py)::`_duplicate_of/_attempt/_evaluate_once`；[通用CLI代末处理](../../code/heuristic_design/core/execution.py)第140–154行；[H阶段互补函数](../../code/fjsp_usage/research/sets.py)；[B1生命周期与接续](../../tools/b1_p1_resume.py)。

## 4. 行为多样性：5→3→2到底是什么

### 4.1 分组定义及本次复核

[physical_schedule()](../../tools/usage_mechanism_ablation.py)把每道工序表示为：

```text
(job, operation, machine, start, end)
```

按这些字段排序，再连同makespan形成物理排程对象。排序消除了提交顺序影响，**保留机器分配和起止时间**，不是只比较Cmax。每个U必须有21个完整实例；依固定实例顺序构造21个物理排程SHA的向量，向量完全相同才同组。

原计算可见[旧派生脚本](../b1-ns-recovery-B-execution-20261023/derive_results.py)第280–283行；最新统计保存在[第二代收尾核验](../b1-p1-to-p2-T15-seed501-20261027-v1/Closeout_summary.json)。本次又直接比较每个工序的原始物理排程对象，并验证其SHA及复检SHA一致，重新得到5／3／2；不是照抄摘要。[成员分组CSV](B1种群物理排程分组.csv)／[逐组成员与源码key](证据核验.json)。

|种群|U数／AST key数|完整21实例物理排程组|冠军Fitness|平均Fitness|
|---|---:|---:|---:|---:|
|P0|5／5|5|−2.115159624700|−2.401808986957|
|P1|5／5|3|−2.115159624700|−2.201894548463|
|P2|5／5|2|−2.092337613385|−2.110595222437|

本批按Cmax向量分组恰好也得到5／3／2，但原方法比较完整物理排程，不能将“本次数量恰好相同”当作两种指标普遍等价。

### 4.2 最新P2：究竟是策略相似，还是不同H碰巧同排程？

P2不是“五个U都一样”，而是**四个同一观察行为组＋一个不同冠军**：

|P2成员|观察到的3800步输出|与旧冠军的关系|
|---|---|---|
|`B/g0000/000006`|SELECT H1 3762步、H5 38步；MIX 0步|旧组代表|
|`B/g0000/000008`|同上，完整输出序列也相同|21实例最终物理排程和动作提交序列全同|
|`B/g0001/000000`|同上，完整输出序列也相同|同上|
|`B/g0001/000006`|同上，完整输出序列也相同；代码有MIX分支但未执行|同上|
|新冠军`B/g0001/000001`|SELECT H1 3744步、H5 28步；H0/H8 MIX 21步、H8/H9 MIX 7步|形成另一物理排程组，Fitness提高|

逐项输出统计及提交序列核验见[P2实际利用行为核验](P2实际利用行为核验.json)。

因此，**对最新P2这四个U，证据支持“代码不同，但在这批实际轨迹上的有效利用行为已经相同”**，不是“实际选了不同H或权重，碰巧得到相同结果”。四者完整原始mode/vector序列、有效support/weight序列的哈希均相同；21实例`commit_sequence_sha256`也逐项相同。它们在别的状态仍可能不同，不能称普遍程序等价。

新冠军与旧组的21个物理排程指纹均不同；其中Cmax仍有4个实例持平，说明“Cmax相同”比“物理排程相同”更弱。收益是11胜6负4平，不能把28步MIX自动解释为收益原因：其条件和单成员路径也有变化，没有做对应因果消融。

**另一种情况在别的历史实验确实存在。** 既有[CROSS解释性分析](../cross-feedback-ab-explanation-20261025-v1/REPORT_ZH.md)记录，`pair_05_r2_B`实际调用过H5，却与较差父代的H0/H9程序在全部21实例得到相同物理排程。这支持“成员调用不同不保证终局不同”；该证据只指最终物理排程，不据此声称所有中间状态或提交顺序完全相同。

### 4.3 能否称早熟收敛？

**可以说**：有限训练实例上的观察行为趋同，且AST去重不足以保证行为多样性。代末纯Fitness保留能容纳多个同物理行为的不同源码U。

**还不能说**：已证明过早收敛、已卡住全局最优、或趋同导致了搜索失败。仅一条两代搜索链；P1组数下降但冠军不变，P2进一步下降却出现新冠军，数据不支持“多样性越少，质量一定越差”的单调因果关系。纯质量选择也会合理淘汰低质量但独特的行为。

实际谱系：第一代4个新子代进入P1，其中g0/6、g0/8与旧冠军同排程；第二代新冠军来自g0/0和g0/8交叉，说明P1确实被后续利用。P2有3个第二代子代进入，但其中2个仍属于旧行为组。新冠军尚未成为第三代父代，因为计划只有两代。没有与行为保留选择的等预算对照、更多独立搜索重复或可靠的停止后改进概率估计。

### 4.4 已有共同状态证据，范围是什么

- [10H共同状态库](../h10-decision-diversity-v1-20261020/sampled_states.jsonl.gz)：384条记录、364个不同物理状态，含七状态、合法动作、10H原始评分、排序与选择。核对其H key顺序与最新B1一致。
- [旧U状态分析](../u-state-behavior-v1-20261020/Evidence_index.json)：旧seed301的20个有效U，共76000步、420条实例成绩，已有状态与分支轨迹。连接缓存评分得到517个候选—状态配对、219个不同物理状态；其中42个配对的previous_heuristic与driver不同，不能叫七输入完全一致的跨U比较。
- 这些证据不自动覆盖最新B1所有U。新B1主记录有逐步输出和终局排程，没有完整七状态／合法动作轨迹；静态selector_diagnostics不补足动态分支覆盖。
- 最新B1可在旧固定状态库上做**新的离线U输出计算**，并用已有10H评分重算动作，不需完整求解；但本轮未执行U或H。此类共同状态探针与各策略自己的真实轨迹是两种不同证据。

### 5.2 哪些需要完整求解，哪些不需要

1. **现成数据直接足够**：总体／逐实例成绩、胜负、终局排程组、源码／AST、B1/B2按进度的成员／权重使用，均不需新增求解。
2. **可做轻量离线探针**：新U在旧固定七状态上的输出、分支覆盖；已有完整H评分列时的动作重算。会执行候选U，但不运行完整排程；仍需独立冻结范围和资源限制。本轮没有执行。
3. **未来运行时最小加日志**：在已有主求解中记录state、support、weights、chosen、branch计数，可避免第三遍求解。观察器必须做行为回归，不能因日志改变策略语义。
4. **仅凭现有文件不足的项目**：新U在其自身轨迹上缺失的其他状态／动态分支记录，以及“某状态选另一动作是否更好”。如无法从真实轨迹恢复，前者需授权回放或重新求解，后者需受控续排；新U的最终Fitness必须完整排程，不能以影子动作频率代替。

物理排程排序表与commit哈希本身都不能逆推出完整七状态序列。若没有实际chosen序列，不应拿一个自行猜出的提交顺序冒充真实原轨迹。

### 5.3 Feedback-guided Evolution：准备程度与最小建议

- **已有能力**：已实现可认证的父代成绩绑定；总分反馈A/B已做过；逐实例数值和有限行为摘要可以从已有结果提取。无需改变U在线七输入，也不需要在线LLM。
- **缺口**：没有统一、跨执行器的反馈schema；没有把逐实例差异或行为摘要真正接入正式生成；新认证器缺逐步状态、权重分布与动态分支日志。已有小A/B未显示总分反馈一致收益，不能保证换更长反馈就有效。
- **建议修改位置（仅建议）**：独立新渲染适配器，参考`cross_feedback_ab.feedback/render`；用Parents/完整result读取字段，在请求前绑定代码key、实例与LB身份。若记录不足，再考虑`runtime._worker`／认证worker的被动日志，不改调度决策函数。
- **最小可行改动**：先利用现成认证成绩做有界结构化反馈；不足的信息标unknown。无需先引入额外反思调用、长期记忆或新的状态特征。本报告不制定新预算或启动实验。
- **统计与泄漏边界**：训练反馈用于搜索本身不是违规泄漏，但会增加训练适应；不能将旧validation11/test28当新确认数据或把确认结果送回生成。整体分差不是分支因果，按实例分组有小样本与事后挑组风险；Cmax与归一化贡献不能混用。
- **公平对照需冻结**：H与编号、H描述文本、U空间、共同P0与先验、父代任务／顺序、模型和参数、逻辑／API尝试预算、失效与缓存计账、train/LB/求解seed、超时／复检／退出规则、反馈长度与额外调用成本、选择策略及分析口径。若要独立检验反思，B与反思条件应获得相同事实信息，额外调用和Token单列。

### 5.4 Diversity-aware Evolution：五类指标能准备到什么程度

|指标|反映什么|现有资产是否足够|主要限制|
|---|---|---|---|
|源码／AST差异|程序结构是否相同|可以；当前已按AST去重，事后结构相似分析也有|最弱行为代理：四个不同AST仍可同输出|

- **已有能力**：AST key、实际解码决策、完整排程指纹、部分共同状态全10H评分，以及可选Coverage工具。尚无正式使用这些指标改父代选择或生存选择的证据。
- **缺口**：统一冻结的行为探针集、全部候选的同条件输出／动作向量、异常和浮点同分规则、行为采集开销计账，以及相同候选预算下的选择机制对照。
- **建议修改位置（仅建议）**：以独立新适配器接入`Search`的父代／代末选择或当前`core.search.survive()`，行为签名计算放独立离线分析／记录模块；不能直接修改历史函数、重写旧Fitness或旧P2。
- **最小可行改动**：先形成可核验行为签名表，检查哪一层真正区分当前重复群体，再决定是否需要选择干预。没有先给一个未经验证的“Fitness＋多样性权重”公式。
- **公平对照需冻结**：与反馈方向共有的条件外，还要固定行为定义、状态库来源与采样、历史输入处理、参考状态数量、距离／同分规则和额外成本。若同时改反馈与选择，无法解释是哪一项造成差异，应分开研究。

## 6. 研究讨论用总结

### 三条由代码和运行证据确认的事实

1. 常规生成确实没有接收真实父代成绩向量；数值反馈仅见于独立CROSS B组。不是“LLM已经知道逐实例好坏但没有利用”。192份实际Prompt重建可追溯。
2. U搜索是排名加权父代抽样、代内冻结、代末父子合并按Fitness截前N；AST去重之外，没有启用U行为新颖性选择。H阶段互补选择不能算作Tier 2已具备的行为选择。
3. B1的完整物理排程组由5降到3再降到2，P2四个U甚至在这批轨迹中完整输出和提交顺序相同；同时第二代冠军改善，不能把趋同直接判成搜索失败。

### 两条值得验证、但尚未证实的假设

1. 匹配身份、限制长度的逐实例／行为事实可能比只给两父代总分更有助于生成；当前总分A/B不支持直接认定它成立，额外文字长度也可能是混杂因素。
2. 在保持主Fitness不变的独立选择机制中识别并减少同一观察行为的重复占位，可能提高有限预算的探索覆盖；也可能保留更多低质量程序、降低短期质量，尚无受控证据。

### 两个适合请教师兄的具体问题

1. **应先验证“现成逐实例反馈是否帮助生成”，还是先验证“同一物理行为占据多个种群名额是否浪费搜索机会”？** 前者数据较齐但总分A/B未见一致收益；后者有5→3→2证据，但尚无趋同导致损失的因果对照。
2. **行为去重应以共同状态动作向量还是完整训练排程为主？** 前者贴近决策但有参考状态偏差，后者已能直接计算却粗且训练依赖；如何让保留多样性具有可解释性，又不改掉主质量目标？

## 附录：WS、MAX、MIN、Borda的U代码到底长什么样

这些独立机制实验用的是**可信callable算子接口**，不是把新算子悄悄塞进原LLM闭合语言。真实入口是[fixed_policy](../../code/fjsp_usage/fusion_v2/execution.py)与[fixed_borda](../../code/fjsp_usage/fusion_v3/execution.py)：

```python
from fjsp_usage.fusion_v2.execution import fixed_policy
from fjsp_usage.fusion_v3.execution import fixed_borda

u_ws = fixed_policy((0, 1), 'WEIGHTED_SUM', size=10)
u_max = fixed_policy((0, 1), 'MAX', size=10)
u_min = fixed_policy((0, 1), 'MIN', size=10)
u_borda = fixed_borda((0, 1), size=10)
```

真实工厂的核心返回值是：

```python
vector = tuple(.5 if i in pair else 0. for i in range(size))
return lambda *state: (operator, vector)
```

为便于阅读，把同一H0/H1工厂结果等价展开如下；**这是工厂展开示例，不是声称四份代码都由LLM生成**：

```python
def U_WS(*state):
    return ('WEIGHTED_SUM', (0.5, 0.5, 0., 0., 0., 0., 0., 0., 0., 0.))

def U_MAX(*state):
    return ('MAX', (0.5, 0.5, 0., 0., 0., 0., 0., 0., 0., 0.))

def U_MIN(*state):
    return ('MIN', (0.5, 0.5, 0., 0., 0., 0., 0., 0., 0., 0.))

def U_Borda(*state):
    return ('BORDA', (0.5, 0.5, 0., 0., 0., 0., 0., 0., 0., 0.))
```

`*state`接收相同七个参数；这里固定策略忽略它们。第二项的前两个正数指定H0/H1。WS的0.5/0.5是真正权重；MAX、MIN、Borda的相等正数是成员支持标记，不是“取极值后再乘0.5”。这些版本拒绝不相等的正标记，不会静默忽略不合法参数。

真正的计算发生在host，而非U里调用H：

|U输出算子|执行器对每个合法动作a做什么|
|---|---|
|WEIGHTED_SUM|每个H在当前动作全集中独立min–max归一化，计算0.5×s0(a)+0.5×s1(a)|
|MAX|同样独立归一化，再计算max(s0(a),s1(a))|
|MIN|同样独立归一化，再计算min(s0(a),s1(a))；最后仍选融合分最高的动作|
|BORDA|对每个H的动作原始评分按高分优先转为名次积分，同分取平均名次，再加和；实际实现用双倍整数积分，排序不变|

最后四者都在合法动作中取最高融合分，动作精确同分用原job／machine规则。Borda不要求先做min–max：单调归一化通常不改变名次；它有自己的平均名次同分定义。程序位置：[fuse_scores](../../code/fjsp_usage/fusion_v2/execution.py)、[fuse_rank](../../code/fjsp_usage/fusion_v3/execution.py)、[borda_twice/borda_scores](../../code/fjsp_usage/fusion_v3/ranking.py)。

**原LLM搜索里的WS仍是另一种输出写法**：`use_heuristics(七参数)`返回`(1, (0.5, 0.5, 0., 0., 0., 0., 0., 0., 0., 0.))`；1代表MIX。原闭合AST不能直接返回字符串`'MAX'`或用`*state`签名。MAX／MIN／Borda目前是独立算子实验，不是B1两代自由搜索已经开放并演化的算子。
