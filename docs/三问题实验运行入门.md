# 三问题实验运行入门

这份说明回答四件事：实验在比较什么、怎样在终端操作、输出数字是什么意思、暂停以后怎样继续。技术细节见[实验包说明](../experiments/triad/README_ZH.md)，研究决定见[本轮任务总览](https://app.notion.com/p/41704e0510d781fb982cee184a4855a9)。

本轮目标是准备完整实验包，由你在终端或集群上手动运行。写好了脚本、离线检查通过、真实实验跑完，是三个不同阶段。当前是否能启动某组实验，以检查命令给出的缺项和最终确认配置为准。

## 1. 先理解这个实验

我们先准备一组启发式规则，称为H集合。每条H像一种做事策略。然后让大模型生成和演化一个选择程序U。

求解每道题时，U读取当前的14项共同状态信息，选出一条H；这条H决定下一步的具体动作。提交动作、更新状态，再进行下一步。求解过程不请求大模型；模型请求发生在搜索程序的阶段。

要比较的三种做法：

| 做法 | 具体在做什么 | 回答什么问题 |
| --- | --- | --- |
| 双层方法 | 先冻结H集合，再搜索选择程序U | 根据状态换规则是否有帮助 |
| 最佳固定H | 从同一集合选一条，在所有题中始终使用它 | U能否超过该集合中训练表现最好的固定规则 |
| 单规则EoH | 直接生成、演化H，每个候选H独自完成整道题 | 直接搜索动作规则与搜索选择程序相比如何 |

“最佳固定H”按整个训练集选择一条，不能每道题事后挑不同的最优H。已有结果只有在H、数据、参照和求解规则兼容时才能复用。

三个问题都做双层方法和EoH，共六个需要请求模型的实验组：

| 问题 | 通俗解释 | 双层方法编号 | EoH编号 | 最终成本 |
| --- | --- | --- | --- | --- |
| FJSP | 给工序安排机器和加工顺序 | fjsp-u | fjsp-eoh | 全部工序完成的时间，越小越好 |
| TSP | 访问所有城市并回到起点 | tsp-u | tsp-eoh | 总路程，越小越好 |
| OBP | 物品依次到达，立即决定放哪个箱 | obp-u | obp-eoh | 实际用过的箱数，越少越好 |

OBP本轮采用的定义稿为“预设N箱版”：总物品数N和容量公开，保留N个永久编号箱。H只看到当前所有可放箱的剩余容量，包括每一个空箱，不看不可行箱或未来物品。已有旧箱能放时，仍允许主动开新箱。U仍然只选H，不直接选箱。

## 2. 一次长实验怎样进行

1. **准备输入**：确定H、训练题目、参照值和配置，并记录文件身份。
2. **初始化**：生成第一批候选程序，达到要求才进入演化。这部分尝试另计。
3. **演化1000次尝试**：按方法规定生成新程序，用完整训练集评价，再决定保留哪些。
4. **保存冠军**：从约定范围内完整有效的候选中，按训练J最小、固定编号平局规则选择。
5. **独立重复**：换搜索种子，从头初始化和搜索，不复制另一份运行的种群或冠军。
6. **汇总**：保留全部运行及失败，比较各次冠军、均值、波动和曲线。留出评价按另外确认的用途执行。

“1000次”是演化生成尝试，不是1000个有效程序，也不是1000代。失败、无效和重复也消耗尝试。初始化和H构建各自另有上限，不能从演化额度中偷偷借用。

当前FJSP U501的种群为5，每代5次交叉、5次独立变异，因此1000次演化对应100代。不能把这一代数关系套用到原生EoH。

一个种子是一份独立搜索。种群里的5个程序、同一程序的两遍复核、21道训练题，都不是5次、2次或21次独立搜索。重复次数按最终确认清单执行；建议值不等于已批准值。

## 3. 先分清三类命令

| 类型 | 例子 | 会做什么 |
| --- | --- | --- |
| 只检查或读取 | plan、check-only、status、query | 读取配置、进度或队列，不请求模型、不求解 |
| 准备和整理文件 | prepare、summary、export、stage、fetch | 可能写计划、导出、上传或下载文件；本身不开始搜索 |
| 真正运行 | run、resume、submit、build-run、fixed-run、lkh-run | 根据命令请求模型、求解或提交作业，必须核对批准范围 |

“无API”不等于“没有计算”：固定H评价和LKH可以不请求模型，但仍会求解。check-only才明确是不请求模型、不求解、不读取真实密钥的检查。

plan列出六组配置、缺项和预算，不创建运行、不读密钥、不求解。当前配置还有待确认值时，可能看到：

~~~json
  "seed": null,
  "status": "pending",
  "pending": ["repeat_count", "search_seeds"],

    "evolution_attempts": 1000,
~~~

要单独检查一组，以下命令可直接执行，不会启动实验：

把obp-u.json换为六组中对应的配置名即可。返回ready=false并列出pending时，是检查发现尚不能启动；ready=true也只表示本次检查通过，不代表获得付费授权或真实实验已完成。


## 5. 参数确认后，怎样在Mac启动一份实验

下面是**命令格式模板**。中文参数必须替换为已确认清单中的值，当前不要直接执行模板：

~~~bash
bash experiments/triad/mac.sh run \
  --experiment 实验组 \
  --seed 搜索种子 \
  --allow-api --allow-solves \
  --approve-total 该次累计上限
~~~

| 参数 | 含义 |
| --- | --- |
| --experiment | 六组编号中的一个，例如fjsp-eoh |
| --seed | 清单中已确认的搜索种子 |
| --allow-api | 明确允许本次请求模型 |
| --allow-solves | 明确允许本次评价候选程序 |
| --approve-total | 本次选中运行的累计请求额度，不是“再加这么多” |

实际值从最终交付表读取，不把说明里的方法名、种子示例或建议预算当作批准配置。

运行时使用一个终端，另开一个终端查看：

~~~bash
bash experiments/triad/mac.sh status
~~~

终端一段时间没有新文字，不一定卡住：可能正在等待模型、评价候选，或只在完成任务后更新进度。先查status，不要再执行一次run。

暂停和恢复也按同一批次选择原实验组及种子：

~~~bash
# 模板：只请求安全暂停，不是立即杀进程
bash experiments/triad/mac.sh pause --experiment 实验组 --seed 搜索种子

# 模板：恢复原运行，承认原累计上限，不追加额度
bash experiments/triad/mac.sh resume \
  --experiment 实验组 --seed 搜索种子 \
  --allow-api --allow-solves --approve-total 原累计上限
~~~

暂停请求发出后，等正在处理的任务结算，并确认phase为paused、writer_lock为false、没有未知发送或未结算评价，再关闭运行环境。不要删锁或直接用run代替resume。

批次入口还支持显式--all，但这会选中多份运行；批准额度须等于所选运行的累计上限之和。首次正式使用建议按交付清单一份一份执行。同一模型账户在Mac和集群上合计只激活一个生成任务；本地文件锁不能自动约束另一台机器。

## 6. 集群怎样操作

可以在Mac终端使用cluster.py统一完成连接、上传、提交和取回。密码交给SSH终端处理，不写进命令或日志。

以下是真实存在的准备命令，不会提交搜索作业：

~~~bash

  experiments/triad/cluster.py inspect

/Users/DDXQL/Developer/cluster-deployment/mac-portability-env-v2/bin/python -s -B \
  experiments/triad/cluster.py stage

/Users/DDXQL/Developer/cluster-deployment/mac-portability-env-v2/bin/python -s -B \
  experiments/triad/cluster.py prepare
~~~

| 操作 | 方向或作用 |
| --- | --- |
| inspect | 只读检查集群环境与资源 |
| stage | Mac→集群，上传当前指定版本的包并核验 |
| prepare | 上传配置、转换为集群路径并准备运行清单 |
| submit | 将指定实验交给Slurm调度，可能进入排队 |
| query | 查询该次提交的队列和记账状态 |
| pause | 向原实验发送安全暂停请求 |
| resume | 为原运行提交恢复作业，沿用原额度 |
| fetch | 集群→Mac，取回已结束作业的结果并校验 |
| summary | 取回批次汇总，不等于下载全部原始结果 |

stage依赖交付包和SHA文件已经存在；若尚未打包，它会拒绝，不会自己构建或随意选择旧ZIP。当前配置未冻结时，prepare可能只能登记缺项，submit仍会拒绝。

resume模板与submit相同，只将操作名改为resume；它恢复原运行，不代表批准新预算。pause只需要选定实验组和种子，不携带请求授权参数。

## 7. 终端输出怎么看

### 先看“目前处于哪一步”

| 输出 | 通俗含义 | 下一步 |
| --- | --- | --- |
| pending、PROTOCOL_PENDING | 条件还没齐，例如参照、H或批准参数缺失 | 按pending列表补输入，不是反复重启 |
| not_started | 计划中有这份运行，尚未启动 | 确认配置和账户安排后再启动 |
| configured | 计划中的配置字段齐了 | 继续check-only；不等于已经运行或有授权 |
| prepared | 运行文件已准备好 | 尚未开始搜索 |
| launching、running | 正在启动或运行 | 查看进度，避免重复run |
| paused | 原运行已暂停 | 查原因，符合恢复条件后用resume |
| completed | 该份搜索按其规则结束 | 导出，核对额度及候选有效性，再汇总 |
| initialization_incomplete | 上限内没收集齐初始候选 | 保留失败，不偷偷补尝试或换种子 |
| expired | 剩余时间不足以安全开始下一任务，或原时间窗口已到 | 保留进度；不要重置时钟冒充续跑 |
| stopped、blocked、requires_investigation=true | 需要核查的异常停止 | 保留日志、检查点和锁，先判断原因 |
| unknown_submission | 不能确定上次是否提交成功 | 先查原作业，不能再提交一遍 |
| evidence_error | 读取或核对某份结果时出现错误 | 检查对应error，不把该次当成0分 |

一次Slurm作业COMPLETED只表示这段作业正常退出，应用可能因时间分段而paused，不能只凭作业终态认定1000次已经完成。

### 再看预算与进度

不同入口字段略有不同，含义以对应字段为准，不强行把它们相加。

| 字段 | 怎么读 |
| --- | --- |
| initialization_attempts | 初始化已占用的生成尝试，独立于演化1000次 |
| evolution_attempts | 演化已占用的尝试；看长实验进度优先看它 |
| generation | 代数；一代可能有多次生成尝试 |
| cursor | 内部处理位置，不直接当作演化次数 |
| request_reservations | 已预留／记账的请求尝试，可能包含尚未结算部分 |
| confirmed_sends | 已确认真正发送的请求数 |
| unknown_sends | 不能确认发送状态的请求；不是0成本，也不能重发 |
| valid_candidates | 通过相应检查的候选记录数；不自动等于不同程序数 |
| valid_unique_evaluations | 使用该字段的入口所报告的有效候选评价计数；不要仅凭字段名推断和其他入口完全同口径 |
| failures、candidate_failures | 候选或处理失败，具体分类看回执；不全是网络错误 |
| duplicates | 重复程序记录，也消耗生成尝试 |
| automatic_retries | 自动重试次数；本轮要求为0 |
| physical_passes | 实际求解的首解first、复核recheck及其开始／完成／失败次数 |
| physical_passes_unsettled | 有开始记录但尚未结束的求解数 |
| known_usage_subtotal | 已知输入／输出token小计，不包含未知部分 |
| unknown_usage_attempts | 有多少次缺少完整用量 |
| actual_cost=null | 费用未知，不是免费 |

例如，初始化8次、演化664次，表示累计占用了672次生成尝试；不能因此断定“672个有效程序”或“实际发送也一定为672次”，仍要分别看发送、失败、重复和在途记录。

首解和复核是为了检查同一候选的求解一致性；两遍求解不能算两个独立搜索。旧运行或未结算任务的计数以原账本为准。

### 然后看成绩

| 字段 | 含义 |
| --- | --- |
| best_J | 当前已完整评价候选中的最好训练J，越小越好 |
| champion_id | 这条候选的编号，便于找到程序和逐题结果 |
| raw_cost | 某道题的原始成本：完工时间、路线长度或箱数 |
| reference | 该道题固定的比较参照，不自动等于最优解 |
| J、score | 相对参照的差距，按本轮定义计算 |
| mean_J | 多份已完成有效运行的平均J |
| sample_std_J | 不同搜索运行的波动；样本少于2次时为null |

本轮J＝各题“(成本−参照)/参照”的平均值。J＝1不表示只差1%，也不直接表示比另一方法差100%。比较两条方法时，应查看同一协议、同一组题的J及原始成本。

内部fitness可能保存−J以复用原生搜索程序；对外看J最小化。不要把旧负Fitness和新J混到同一张图里。

best_J在运行中只是训练中途最好值；completed后的冠军仍不自动代表未见实例上的表现。多个搜索种子主要观察搜索稳定性，泛化需要另外确认的留出评价。

### 集群回执和普通错误

| 输出 | 含义 |
| --- | --- |
| job_id | Slurm接收提交后分配的作业编号 |
| PENDING | 作业排队，尚未开始计算 |
| RUNNING | 作业正在计算节点执行 |
| COMPLETED、exit_code=0:0 | 这段作业正常结束，还要看应用phase |
| FAILED、TIMEOUT、OUT_OF_MEMORY | 作业失败、超时或内存不足；保留结果和原因 |
| active=true | 作业仍在队列中，通常还不能取回最终结果 |
| uploaded=true | 包已上传，不代表实验跑过 |
| retrieved=true | 已下载结果，不代表该实验成功 |
| result_hashes_verified=true | 下载内容与文件清单相符，不是算法正确性结论 |
| error_type、error | 错误类别和具体原因，先读error |
| automatic_retry=false | 脚本没有替你再次请求或提交 |

pause_reason可能保留上一次暂停的文字。判断当前状态应结合phase、最新请求／事件时间、在途记录和writer_lock，不仅看一条旧原因。
