# 长实验自动续跑与结果导出

新配置入口及日常操作见[研究人员实验操作手册](研究人员实验操作手册.md)。下文保留最初 R15 批次入口的参数和调度说明。

新版每个种子的目标是收到 1000 个演化候选。每条正常返回都占一个名额，包括语法错误、接口不合规、重复、评价失败或成绩较差的程序。初始化和第一层 H 构建分别计账。运行期间的真实发送、重试、未发出预留、已知 token 和用量未知记录各有字段。

本入口供新批次使用。TSP R13 的 U501 和 EoH501 继续按原 1000 次演化尝试运行。通用运行器接入 TSP U／EoH、OBP U／EoH 和 FJSP EoH。FJSP U503 使用另一套已冻结的分批执行器，新计数暂未接入该入口。OBP U 仍需要实际的 H401 冻结资产。

## 1. 预览

在新版源树或未来的独立部署目录打开终端。下面以 TSP 第 502 个种子为例。若只运行一组，追加 `--group tsp-u` 或 `--group tsp-eoh`。其他批次用 `--help` 查看。

```bash
HDL_P=/public2/home/qiuqian/hdl-envs/portable-v2/bin/python
HDL_POLICY=configurations/six-groups-20261116/candidate-policy.draft.json
"$HDL_P" -s -B experiments/triad/campaign.py preview --batch tsp502 --policy "$HDL_POLICY"
```

预览只检查本批配置和资产。它输出每组的 `pending`、原累计上限和共享 API 并发数。预览不会读取密钥、调用模型、求解或提交 Slurm。TSP 应绑定已核验的 LKH train20 参照，继续复用冻结的 10H。

部署用新目录 `/public2/home/qiuqian/hdl-deploy/triad-candidate-runtime-20261119-r15`。发布包从冻结 R13 资产包和新版 Git 提交生成，含文件清单和外部 SHA-256。实际参照文件沿用 R13 的已核验结果，在新目录中核对原文件哈希后用 `six_ops.py bind-tsp --asset` 绑定。旧目录里的运行记录、共享账本和原请求授权都不随发布包复制。

### 待研究总览确认的值

| 参数 | 草案值 |
| --- | --- |
| 空响应 | 排除。可选择计为无效候选 |
| 模型身份已核对且明确因长度截断的响应 | 排除。可选择计为无效候选 |
| 每个演化槽 | 最多 2 次预留，第二次等待 5 秒。只有允许补发的临时故障能用到第二次 |
| 每个种子的演化预留上限 | 1100，包含已确认未发送和结果未知的预留。初始化最多 20 个原槽位，沿用原初始化政策 |
| 连续失败 | 草案建议连续 5 个槽未返回时暂停该种子。收到可辨认的回复后清零。可设 `0` 关闭此阈值，仍受演化请求上限和账户保护约束 |
| HTTP 429 | 共享发送等待 30 秒。默认保留失败槽，供应商明确拒绝且采用记录允许时，可有限补发 |

每次补发使用新的物理请求 ID，保留已有回执。收到 HTTP 520、522 或 524，且账本确认发送、客户端工作进程已结束时，按收到错误响应处理。失败仍计入请求预算，缺失用量保留为未知，同一槽不重发。网络超时如果没有终态响应、发送状态不清或工作进程没结清，共享 STOP 会保留相关证据。鉴权、额度、账户所有权或租约冲突也会阻止新请求。

在本地队列超时的已确认未发送请求，只结算自己的占位。另一组持有的合法发送锁继续有效。共享文件系统无法确认账本或锁归属时，继续保留待核查证据。

## 2. 一次授权并启动

实施研究采用后，把采用记录和参数写入一份独立的配置文件。下面的 2240 来自草案示例的两组，每组最多 20 次初始化预留加 1100 次演化预留。配置改变后，以预览返回的 `original_aggregate_cap` 为准。

```bash
HDL_POLICY=preparations/operations/candidate-policy.adopted.json
"$HDL_P" -s -B experiments/triad/campaign.py preview --batch tsp502 --policy "$HDL_POLICY"

"$HDL_P" -s -B experiments/triad/campaign.py start \
  --batch tsp502 --policy "$HDL_POLICY" \
  --submit --allow-api --allow-solves --approve-requests 2240 \
  --confirm-exclusive-account --exclusive-hours 72 \
  --window-hours 48 --wall-seconds 43200 --max-segments 4 \
  --release-account-on-completion
```

第二条命令会提交真实搜索。运行前要核对共享账户已交接、分区允许的资源、上述采用记录和真实执行授权。48 小时是示例运行窗口，从作业首段启动时计。72 小时是本批账户排他期限，从创建计划时计。短批次可用更短的排他期限，须覆盖计划中的运行窗口及实际排队时间。43200 秒是单个搜索作业申请的 Slurm 时限。最多 4 段包括首段。续跑申请时间会按批次剩余时长缩短。

每段退出后，Slurm 的依赖作业检查上段终态、候选计数、请求对账和所有权，再提交下一段。正常时间暂停复用原检查点、种群、随机状态、评价证据和原预算。达到目标、用完预算、达到已批准段数、租约到期、主动暂停或发生需要人工核验的故障，都有各自的终止记录。若一组因自身普通传输故障达到停止阈值，同批另一组可在干净的时间暂停后继续。暂停和恢复期间不需要终端保持连接。

同一批次的两个作业可以先后获得资源。每个作业自行核对本段 Slurm ID、共享账本和原租约，然后在本节点做文件锁检查。同批另一作业在队列中等待时，已分配作业可以开始。该检查的范围是单节点，跨节点共享目录的互斥能力需在部署环境单独验证。

## 3. 查看进度和取回结果

```bash
"$HDL_P" -s -B experiments/triad/campaign.py status --manifest plans/candidate-tsp502/Shared.json
squeue -u "$USER" -o '%.18i %.12T %.10M %j %R'
cat plans/candidate-tsp502/Campaign_result.json
```

| 输出 | 含义 |
| --- | --- |
| `successful_evolution_responses` | 已收到并计入演化目标的候选数 |
| `evolution_requests` | 已结算的演化槽数，包括传输失败 |
| `original_request_cap` | 本种子的请求预留上限 |
| `reason=scientific_complete` | 本批所有种子都达到 1000，且本地回执与 Slurm 终态核对通过 |
| `Campaign_result.json` | 本批最终状态和每组的导出路径。单独的 Slurm `COMPLETED` 只说明进程退出 |

导出目录含冠军程序、逐实例成本、候选表、`API-physical-attempts.csv`、`successful-response-curve.csv` 和对应 SVG。U 的历史 H 构建成本单列，缺少来源账本时记未知。复制原运行目录和日志，再按项目归档流程核验。已经导出和已完成异机备份分开记录。

如果没有自动进入下一段，依次查看 `Campaign_result.json`、`campaign-control/error-*.json` 和 `logs/*-review-*.err`。看到共享 STOP、提交回执不明或未知在途时，先核实原请求或 Slurm 状态。普通运行记录无需用 R11／R13 事故工具复查。

## 4. 离线验收

```bash
python3 -s -B experiments/triad/candidate_runtime_tests.py --target 10
python3 -s -B experiments/triad/candidate_runtime_tests.py --fast-ledger
```

第一条使用本地文件账本验证故障隔离。第二条使用内存中的共享账本跑完两组各 1000 个成功返回，并在分段边界写回账本作为续跑输入。两条都使用合成回复、Mock 评价及模拟的 Slurm 回执。真实部署前仍需确认计算节点可以运行 `squeue`、`sacct` 和提交依赖作业，并核对实际分区时限、作业配额与共享文件系统。[Slurm 依赖作业](https://slurm.schedmd.com/sbatch.html#OPT_dependency) · [Slurm 剩余时限](https://slurm.schedmd.com/squeue.html)

新版部署后，经用户批准，在部署目录提交下面的调度小测。它只运行两个各最多 5 分钟、单核、1 GiB 的 Slurm 作业。第一个在计算节点提交第二个，第二个核对依赖终态和共享目录中的回执。它不读取凭据或实验数据。

```bash
sbatch --parsable --partition=128C_02 --account=wz --qos=normal \
  --nodes=1 --ntasks=1 --cpus-per-task=1 --mem=1024M --time=00:05:00 \
  --job-name=r15-smoke-parent --output="$PWD/r15-smoke-%j.out" \
  experiments/triad/candidate_slurm_smoke.sbatch "$PWD" 128C_02 wz normal
```

第一个日志会打印两个作业 ID 和回执目录。看到目录下的 `child.passed`，才确认该账号能从计算节点提交依赖作业。如果内层提交被拒，自动续跑在该集群上就不可用，需先确定允许的调度方式。正式启用前，还要在计划使用的计算节点上验证共享路径的原子建锁和写入可见性，并用短 Mock 分段确认 Slurm 收尾信号、检查点和依赖作业能够接续。计划跨节点运行时，应在两个不同节点同时做共享锁检查。

## 5. 版本切换

R13 与 R15 各用自己的部署目录、计划和结果。R13 续跑使用 R13 原入口和原检查点。需要切回 R13 工具时，先确认 R15 的作业已终止且共享账户可以安全交接，再进入原 R13 目录。已生成的 R15 检查点及结果留在 R15，按原软件版本继续或归档。
