# “1000个成功返回”的只读差异评估

本页仅评估用户新提出的口径，不实施、不补预算。R13及当前R14仍按1000次演化尝试、初始化另计、每槽一次、累计1020、不自动重试运行。现有旧结果保留原身份，不重新解释成1000个成功返回。

## 新口径需要另行确认的最小决定

“成功返回”建议严格对应V5客户端接纳后的完整响应、即journal请求status=completed，发生在候选解析之前。因此代码无效、AST重复、同分惩罚和评价失败仍可以计一次成功返回；HTTP200但模型不符、拒绝、截断或响应协议不通过，不能默认为成功。此定义尚未采用。

真实发送／保守预留的独立上限、每机会可补发次数和可重试类别仍待确认，不能沿用1020后声称保证获得1000次成功返回。初始化上限20及H401原规则仍单独保留，不能拿未用初始化额度填补演化传输失败。

需要区分成功返回计数、演化机会／算子计划计数、实际尝试／确认发送计数，以及失败／未知记录。补发应复用哪一份已冻结的operator、parents、prompt及随机状态，需要明确；不能失败后偷偷重新抽父代，也不能覆盖旧失败或重放原请求ID。未知发送不自动补发，即便费用或usage未知也不能退款。

## 工程边界

这不只是放宽共享STOP。TSP/OBP涉及triad机会计数、原生EoH commit、任务槽、配置中`api_attempt_cap=init+evolution`的约束及journal重试策略；FJSP冻结U的计数在923781f核心中，若要改变也必须新协议/新源码身份，不能在旧运行上补几次或只修改报告曲线。

V5底层已有有限重试基础，但当前正式绑定要求每候选一次，不代表已批准启用。R14的许可分类清理可作为之后的基础，不能被描述为已实现“1000次成功返回”或已提供补发预算。正式实现范围、物理请求上限及费用边界确认前，所有相关新参数保持待定。
